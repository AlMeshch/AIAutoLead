# ADR-011. Execution работает со снапшотом версии, а не запрашивает её

- **Статус:** Proposed
- **Дата:** 2026-09-06
- **Связанные:** ADR-002 (границы), ADR-008 (versioning), ADR-010 (database per service)
- **Схема:** [`../diagrams/01-service-topology.svg`](../diagrams/01-service-topology.svg)

## Context

`execution-service` не может исполнять граф, не зная его определения: узлы, рёбра, конфиги,
условия переходов. Определение живёт в `workflow_db`, которой владеет `workflow-service`.

Определение нужно не один раз на старте, а **на каждом шаге**: после каждого результата ноды
движок вычисляет следующие узлы, а значит читает рёбра и условия. Для workflow из 30 узлов это
десятки обращений за одно исполнение.

Наивный вариант — синхронный `GET /workflows/{id}/versions/{v}` — создаёт три проблемы:

1. **Связанность по доступности.** Лежит `workflow-service` → не стартует и не продвигается ни
   один execution. Сервис пользовательского CRUD становится критическим путём исполнения;
2. **Латентность.** Сетевой вызов в цикле продвижения графа;
3. **Кэш с инвалидацией.** Кэшировать хочется, но тогда нужен протокол инвалидации — то есть
   ровно та сложность, которой мы избегали.

## Decision

**При создании execution определение published-версии копируется в `execution_db`** — в поле
`execution.workflow_snapshot` (JSONB): узлы, рёбра, конфиги нод, retry policy, ссылки на
креденшелы.

Обоснование, почему это безопасно: по ADR-008 **опубликованная версия immutable**. Копия
неизменяемых данных не может рассинхронизироваться с источником — рассинхрон возможен только
там, где источник меняется. Immutability версии из «гарантии воспроизводимости» превращается в
механизм развязки сервисов.

Дальше движок читает только `execution_db`. `workflow-service` в рантайме исполнения не участвует.

### Что НЕ попадает в снапшот

**`credential_ref` остаётся ссылкой** и резолвится воркером в момент выполнения через
`secrets-service`. Секреты ротируются, и снапшот значения сломал бы ротацию: долгоживущий
execution пошёл бы со старым ключом. Правило: в снапшот попадает то, что immutable по контракту;
всё остальное — по ссылке.

### Локальный read model published-версий

`execution-service` дополнительно держит проекцию published-версий, обновляемую по событию
`workflow.published`. Это нужно не для исполнения, а для admission: проверить, что версия
существует и опубликована, до создания execution. Проекция — кэш, снапшот — источник истины
для конкретного исполнения. Одно не заменяет другое.

## Alternatives

**Синхронный вызов на каждом шаге.** Отклонён по трём причинам выше.

**Синхронный вызов один раз на старте, дальше в памяти.** Отклонён: движок не держит состояние
в памяти между сообщениями — обработка результата ноды может попасть на любую реплику, а после
рестарта состояние восстанавливается из БД. Определение обязано быть durable.

**Только read model по `workflow.published`, без снапшота в execution.** Рассмотрен; отклонён:
не переживает удаление или чистку версии. Execution обязан доехать до конца, даже если версию
удалили из `workflow_db` в процессе. Снапшот привязан к жизненному циклу execution, а не версии.

**Общая БД для workflow и execution.** Отклонён — противоречит ADR-010, и это худший вид
связанности: неявный, через схему.

## Trade-offs

- **Дублирование данных.** Осознанное: это не нормализованная модель, а снимок для
  воспроизводимости;
- **Размер строки.** Граф на 100 узлов с конфигами — примерно 50–200 КБ JSONB. Postgres уводит
  такое в TOAST, читать целиком на каждом шаге дорого. Если профилирование покажет проблему —
  раскладывать снапшот в нормализованные таблицы `execution_node` / `execution_edge` при создании
  execution. Решение отложено до появления замера, форма хранения не влияет на этот ADR;
- **Багфикс в определении версии не подхватывается** уже запущенными executions. Это не дефект,
  а требование воспроизводимости из ADR-008: исполнение, начатое по версии v2, доезжает по v2;
- **`execution_db` растёт быстрее** — нужна политика ретенции (архив снапшотов завершённых
  executions старше N дней).

## Consequences

- `workflow-service` может быть недоступен: новые executions создаются, идущие продвигаются;
- он выпадает из пути исполнения → его SLO мягче, чем у движка. Это влияет на приоритеты
  дежурства и на то, что мониторить в первую очередь;
- валидация при publish (ADR-008) не может опираться на изменяемые внешние данные: всё, что
  проверено на publish, должно остаться верным на момент исполнения. Единственное исключение —
  существование `credential_ref`, которое перепроверяется в рантайме;
- нужен тест: остановить `workflow-service`, запустить execution, убедиться, что он доезжает.
  Без этого теста связанность вернётся незамеченной при первом же рефакторинге.
