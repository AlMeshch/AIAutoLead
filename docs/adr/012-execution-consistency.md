# ADR-012. Модель консистентности выполнения

- **Статус:** Proposed
- **Дата:** 2026-09-06
- **Связанные:** ADR-006 (outbox), ADR-007 (idempotency), ADR-009 (retry), ADR-002 (границы)
- **Схема:** [`../diagrams/03-node-result-path.svg`](../diagrams/03-node-result-path.svg)

## Context

`execution-service` — реактивная машина состояний: она не ждёт результата, а обрабатывает
входящие события `node.completed` / `node.failed` и продвигает граф. Отсюда четыре проблемы
консистентности, каждая со своим механизмом. Их **нельзя подменять друг другом** — это главный
вывод этого ADR.

1. **Конкурентные результаты одного execution.** Две параллельные ветки завершаются
   одновременно, два консьюмера одновременно вычисляют «следующие узлы» на одном execution →
   дублированные шаги или потерянные ветки.
2. **Дубль доставки.** RabbitMQ гарантирует at-least-once; одно и то же событие приходит дважды.
3. **Потеря команды.** Execution записан в Postgres, публикация в RabbitMQ не удалась → execution
   существует, но команда на его продвижение потеряна, и он висит навсегда.
4. **Воркер не вернул результат.** Три разных сбоя с разными симптомами: воркер умер до `ack`;
   воркер сделал `ack` и умер до публикации результата; **воркер жив, но завис** и не делает
   ничего.

## Decision

### 1. Сериализация по `execution_id`

Результаты маршрутизируются через плагин `rabbitmq_consistent_hash_exchange` по ключу
`execution_id` в одну из N очередей `results.0..N-1`, каждая с `prefetch=1`. Все результаты
одного execution попадают в одну очередь и обрабатываются строго последовательно — при competing
consumers и горизонтальном масштабировании.

Оптимистичная блокировка (`execution.version`) остаётся как страховка: при конфликте —
`ROLLBACK` и `nack` с requeue. Она не заменяет сериализацию, а ловит случаи ребаланса шардов.

### 2. `StepExecution` — отдельный агрегат

`Execution` хранит статус и счётчики; шаги — самостоятельный агрегат со ссылкой на execution.

Причина: при одном агрегате `Execution` + все `StepExecution` каждая параллельная ветка
конфликтовала бы по версии агрегата, а на каждый результат ноды пришлось бы загружать все шаги
(для workflow на 100 узлов — 100 строк ради обновления одной).

Продвижение графа читает облегчённую проекцию `execution_progress`, а не полный набор шагов.

### 3. Идемпотентность внутри той же транзакции

```sql
BEGIN;
  INSERT INTO processed_event (event_id) VALUES ($1);  -- UNIQUE
  UPDATE step_execution SET status='SUCCESS', output_ref=$2 WHERE id=$3;
  -- advance(): вычисление следующих узлов, Condition считается здесь, in-process
  INSERT INTO step_execution (..., lease_expires_at) VALUES (...);
  INSERT INTO outbox_event (...) VALUES (...);
COMMIT;
```

Дубль доставки нарушает UNIQUE → `ROLLBACK` → `ack`. Состояние не изменилось. Ключевое: проверка
идемпотентности и изменение состояния — **одна транзакция**. Отдельная проверка «уже
обработано?» перед транзакцией — это гонка, а не защита.

### 4. Lease на шаг + reaper

`step_execution` получает `attempt`, `worker_id`, `lease_expires_at`, `idempotency_key`. Воркер
продлевает lease heartbeat'ом в Redis. Reaper (в процессе `scheduler`, ADR-002) периодически:

```sql
SELECT ... FROM step_execution
WHERE status='RUNNING' AND lease_expires_at < now()
FOR UPDATE SKIP LOCKED;
```

и перевыдаёт задачу **с тем же `idempotency_key`**.

Разделение ответственности, которое нельзя схлопнуть:

| Сбой | Кто ловит |
|------|-----------|
| Дубль доставки | UNIQUE на `event_id` |
| Воркер умер до `ack` | Redelivery RabbitMQ |
| Воркер жив, но завис | **Только reaper** — сообщение не redelivered, оно у живого консьюмера |
| Потеря команды при публикации | Outbox (ADR-006) |

### 5. Порядок: COMMIT → ACK → PUBLISH

`ack` в RabbitMQ — только после `COMMIT`, никогда до. Публикация — не в транзакции, а через
outbox publisher с publisher confirms.

Падение между `COMMIT` и `ack` безопасно: redelivery приводит к повтору, который отсекается на
первой строке транзакции.

### 6. Payload не летает в сообщениях

В сообщении только идентификаторы и `output_ref`. Выход больше 64 КБ уходит в MinIO. Причины:
DLQ хранит сообщения неделями, payload утекает в логи воркера и в span attributes трейсов, а
большие сообщения бьют по throughput брокера.

## Alternatives

**`pg_advisory_xact_lock(hashtext(execution_id))` вместо consistent-hash.** Проще — не нужен
плагин RabbitMQ. Отклонён: держит соединение на всё время транзакции (при пиковой конкурентности
съедает пул), и не даёт естественного шардирования консьюмеров — все реплики конкурируют за все
executions. Остаётся как fallback, если плагин окажется проблемой в эксплуатации.

**Один агрегат `Execution` + `StepExecution`.** Отклонён: конфликты на каждой параллельной ветке
(см. п. 2).

**Только redelivery, без lease и reaper.** Отклонён: не покрывает зависший воркер. Это самый
неприятный сбой на практике — execution висит в `RUNNING` бесконечно, без ошибок в логах, без
сработавших алертов.

**Publish до commit.** Отклонён: даёт фантомную команду на несуществующий шаг при откате
транзакции.

**Готовый оркестратор (Temporal / Cadence).** Закрыл бы пункты 1–5 из коробки. Отклонён
осознанно: демонстрация механики распределённого выполнения — одна из целей проекта, а не
побочный эффект. Требует отдельного ADR-013 с честным сравнением; без него решение выглядит как
незнание альтернативы.

## Trade-offs

- Зависимость от двух плагинов RabbitMQ (`consistent_hash_exchange`, `delayed_message_exchange`)
  — образ брокера собирается свой;
- **Изменение N шардов требует ребаланса.** Пока идёт ребаланс, гарантия сериализации ослаблена
  — тут работает оптимистичная блокировка. N выбирается с запасом (16) и не меняется;
- Heartbeat даёт постоянный фоновый трафик в Redis, пропорциональный числу активных шагов;
- Reaper даёт at-least-once → **идемпотентность обязательна во всех воркерах**, а не только в
  движке. Для HTTP-нод без идемпотентности на стороне внешнего API это принципиально
  недостижимо — такие ноды помечаются `at_most_once` и не перевыдаются, а падают в FAILED;
- Один медленный execution занимает свой шард целиком (`prefetch=1`). Это цена
  последовательности; при 16 шардах и равномерном хеше приемлемо.

## Consequences

**Обязательный тест** — главный артефакт проекта:

```
запустить execution → docker kill воркера посреди шага
→ execution доезжает до конца, каждый шаг выполнен ровно один раз
```

Плюс отдельные тесты: дубль события не меняет состояние; падение между COMMIT и ACK; зависший
воркер (воркер, который получил сообщение и ничего не делает) подхватывается reaper'ом.

**Метрики, без которых механизмы не наблюдаемы:** `outbox_lag_seconds`,
`leases_expired_total`, `duplicate_events_total`, `optimistic_conflicts_total`, глубина
`results.*` и `tasks.*`.

**Открытый вопрос — мёртвые ветки.** Если узел-джойн ждёт все входящие рёбра, а одна ветка
отсечена `Condition`, execution повиснет навсегда: reaper здесь не поможет, потому что шаг не
`RUNNING`, а просто не создан. Требуется явная пометка недостижимых ветвей при вычислении
условия и проверка достижимости джойна при валидации графа (ADR-008). Решается в рамках
семантики графа, но проявляется как liveness-баг этой модели — вынести в отдельный ADR перед
реализацией `Condition`.
